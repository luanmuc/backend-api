## G4 · 同源并发重复外呼

**命令**：`maxConcurrency=1e6` 下同一首歌并发 5 个 `musicUrl`。

```
5 并发结果: OK/OK/OK/OK/OK
上游 oiapi 外呼次数: 5（理想=1）
```

**代码依据**：`inflightCount`（L2466）只是并发**计数**，用于 `inflight >= maxConc` 时跳过本轮；没有"同歌同档共享同一个 Promise"的合并表。

**影响**：App 侧若同时发起播放 + 预加载 + 重试，同一首歌会重复打上游。上游配额是廉价资源，但 429 风险会叠加——而本项目刚为 429 设计了整条退避链路。

**分级的理由**：这不是"错误结果"，只是"多做功"。串行点歌场景（用户实际路径）每次 1 个请求，不受影响。

**未修**：请求合并属于新增机制（共享 Promise 后片段/失败结果如何分发、如何与缓存写点配合都需要设计），不是一行修补。

## G6 · 安全面

**命令**：让上游依次返回四种非法 URL，观察是否交付。

```
javascript:alert(1)      → LINK_EXPIRED（不交付）
file:///etc/passwd       → LINK_EXPIRED（不交付）
data:audio/mp3;base64,xx → LINK_EXPIRED（不交付）
超长 https://a…(3000)    → LINK_EXPIRED（不交付）
200KB songmid            → LINK_EXPIRED，耗时 7ms
```

**事实**：四种都**不会被交付给 App**。防护是两道，不是一道：

1. `validateUrl`（L1497）用 `HTTP_URL_REGEX = /^https?:\/\//i` 做**显式协议白名单**。实测：`javascript:` / `file:` / `data:` / 协议相对 `//evil` 全部 `false`，`https://` / `HTTP://` / `HTTPS://` 全部 `true`。
2. 闸门开启时还有验真兜底。

实测代表码显示 `LINK_EXPIRED` 而不是 `PARAM_ERROR`，是因为非法 URL 先撞上了验真判据——**不代表没有白名单**。（初稿这里写"无协议白名单"，是未核实就下的推断，已纠正。）

**残留风险**：`verifyDelivery=false` 时仍由 `validateUrl` 单独守住，两道相互独立；但白名单只认 `http(s)`，对"合法 https 但指向内网/本地地址"没有拦截（本项目不含该场景，记为边界）。

### 11.4b 错误码契约：12 个码 vs App 6 个映射（D-27，推送前补查发现）

G11 原来只对照了**字段名**（`HealthItem` vs 快照），没对照**错误码集合**。

音源 `ERROR_CODES` 实有 **12 个**：`NETWORK_TIMEOUT` / `NETWORK_ERROR` / `PARAM_ERROR` / `RATE_LIMIT` / `SERVER_ERROR` / `NOT_FOUND` / `MISMATCH` / `CONFIG_ERROR` / `LINK_EXPIRED` / `PREVIEW_FRAGMENT` / `NOT_AUDIO` / `STREAM_PLAYLIST`。

App `src/core/music/utils.ts` 的 `FAIL_CODE_ZH` 只有 **6 个**，而且其中**两个码名对不上**：

| 音源实际抛出 | App 表里的键 | 结果 |
|---|---|---|
| `NETWORK_TIMEOUT` | `TIMEOUT` | 未命中 → 显示英文码 |
| `RATE_LIMIT` | `TOO_MANY_REQUESTS` | 未命中 → 显示英文码 |

`FAIL_CODE_ZH[code] || code` 的兜底是把码原文交给用户，所以 `LINK_EXPIRED`、`PREVIEW_FRAGMENT`（「只拿到试听片段」）这些**用户最该看懂**的码，反而全是英文。

**修**：App 侧补齐 12 码，两个旧码名保留兼容（其他源与历史路径在用）。逐码核对后**缺失 0**。

**教训**：字段名对得上 ≠ 契约对得上，**枚举值集合**也要对。这条和"跨仓硬判据"是同一类错误换了个字段。

### 12.3 结论

- 网络是通的，上面对照证明了这点；
- suyinKuwo 不是"死了"，是**链接时效差**：搜索/解析都正常，交付的 CDN 链接高概率立即失效；
- 这正好说明 D-20 修复里那道验真闸门是必要的——没有它，410 链接会直接交给播放器；
- 但链结构上的问题没变：**tx / mg / kg 三个平台只有 suyinKuwo 一根独苗**。它一失效，这三个平台就是"点了必失败"，而 App 侧三个平台按钮都在。

连续 10 次请求在第 6 次就触发。错开 4 秒窗口单独复测 mg / kg 的 128k，**两次都成功**
（249ms / 123ms，子源 suyinKuwo）。

1. **kw 的 flac 由 `xinghaiBackend` 交付**——星海后端不是只挂在那里当备用，它真能出 flac
2. 其余四平台走 `suyinKuwo`，全部交付
3. 之前「2/3 链接立刻 410」是**特定档位/特定时刻**的观察，不能外推成平台级结论
4. 这条同时说明 **D-20 那道 1KB 验真闸门是必要的**：链接确实会时好时坏，闸门拦的是"坏的那一刻"

**口径已修正**：`README.md` 可用性表与 `AUDIT_PLAN_v10.md` §7 第 1 条原来写「点开大概率失败」，
改为「链接时效逐次波动，不能断言大概率失败；端到端矩阵实测 10/10 可交付」。

### 1. 错误码归因不准（C 级，已修）

G6 实测：上游返回 `javascript:` / `file:` / `data:` 时，最终代表码是 **`LINK_EXPIRED`**（语义="签名 URL 过期/410"），而不是 `PARAM_ERROR`（语义="URL 格式非法"）。

真实原因：`validateUrl` 拒绝后抛的是 `PARAM_ERROR`，但验真环节也失败，最终代表码取决于哪条先被记为"代表性失败"。结果是**诊断时会以为链接过期，实际是协议非法**。

不影响安全（都不交付），只影响排障。**已修（a57d593）**：新增 `assertDeliverableUrl`，非法协议直接 `PARAM_ERROR`，复现对比已验证。

### 5. D-24 的兜底比我最初判断的窄

`setApiSource` 内部有 catch，失败时会去找"另一个非 disabled 源"并切过去。所以"切源失败"不等于 App 全挂。

但 `apiSourceInfo.find(api => !api.disabled)` 在只剩新源一个时，找到的就是新源本身 → `api.id == 当前 setting` → 不再递归 → 停在这里。

**结论**：新源加载失败 + 无备用源 = 静音，且旧源已在上一行删掉，无法回退到"用旧源"。这是 D-24 的真实边界。

### 6. G5 的"heap 未增长"不能当结论

`heapUsed 6.7MB → 5.7MB` 是下降，原因是 GC 时机，不代表"内存可控"。

**已补（成功路径长跑，`node --expose-gc`）**：

| 场景 | 外呼 | heap 采样 | 结论 |
|---|---|---|---|
| 同歌 200 次 | **2 次**（199 次命中成功缓存） | 3.9 → 4.0 MB | 缓存生效，无增长 |
| 不同歌 200 次 | 400 次（每首 2 个关键词） | 4.3 → 4.6 MB | 平稳 |
| 不同歌 600 次（超 `CACHE_MAX_SIZE=500`） | 1200 次 | 4.3 → 4.6 → 4.6 → 4.7 MB | 超限淘汰生效，**不线性增长** |

这条比读内部表更硬：不依赖"表里有多少条"，直接用"199 次请求只打 2 次上游"证明缓存在起作用。
