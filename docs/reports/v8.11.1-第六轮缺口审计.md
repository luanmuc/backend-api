
**事实**：`grep -c "audit/" .github/workflows/*.yml` = 0。

**后果**：第五轮认定的 22 条 A 级断言（含 D-20 的缓存单写点 M14、INV2b 换源、FAULT8c 限流标记）**一条都不在 CI**。任何人改坏 `setCachedUrl` 写点或熔断复位，CI 仍是绿的。

**这不是"漏了个 step"，是"本地守、远端不守"**：本地 13 项门禁只有提交者手动跑才有效，而 PR 合并只看 CI。

## G2 · 平台覆盖（tx/mg/kg 单点）

**命令**：宽容上游（JSON 一律给链接、音频直链一律给音频），对五平台各调一次 `musicUrl`。

```
kw: OK  chain=[suyinKuwo, xinghaiBackend, helloworldKw, kuwoOfficial, changqingVip, nianxinVip, ikun, huibq]
wy: OK  chain=[suyin163, wyOuter, ikun, suyinKuwo, huibq]
tx: OK  chain=[suyinKuwo]
mg: OK  chain=[suyinKuwo]
kg: OK  chain=[suyinKuwo]
```

**事实两条**：

1. tx / mg / kg 三平台**只有酷我一个源**。`suyinKuwo` 一旦熔断、限流退避、或该档被短路，这三个平台**没有任何备用**——直接全挂。
2. 这三个平台用的是 kw 源的取链接口，歌曲 ID 体系不同（tx/mg/kg 的 songmid 传给酷我接口）。宽容上游下"OK"只证明代码不崩，**不证明取到的是同一首歌**。

**风险分级**：第 2 条是 N 组"假成功/错内容"的典型场景，前五轮从未覆盖。但它是**产品能力边界**（本来就没有对应平台的源），不是代码缺陷——除非能证明用户实际在播 tx/mg 的歌并拿到错歌。

**未做**：真实上游验证（需要真实 API 且会消耗配额）。记为已知边界。

## G3 · 配置面

**命令**：花括号配平解析 `USER_CONFIG` 顶层键，与 `ALLOWED_KEYS`、`PARAM_LIMITS` 三方比对。

```
USER_CONFIG 顶层键: 39
ALLOWED_KEYS: 15
白名单有但未注入声明: 无          ← MEM1 的坑确实已修
声明了但不在白名单: 24
```

**事实**：39 个键全部有注入声明（`__lxSourceConfig` 能读到），但只有 15 个能通过 `config` action 写。

**含义**：`verifyDelivery` / `fragmentFallback` / `verifyDurRatio` 等 9 个闸门键 + 另 15 个参数键，**App 端改不了**，只能改脚本重发。所谓"可关闭、可回滚"在 App 侧不成立，只有"可改脚本"。

**已修**：`docs/ARCHITECTURE.md` 原写"14 个 ALLOWED_KEYS + 9 个闸门键不开放"，改为"15 个"并补"24 个键只读（含 9 个闸门键）"。

## G4 · 同源并发重复外呼

**命令**：`maxConcurrency=1e6` 下同一首歌并发 5 个 `musicUrl`。

```
5 并发结果: OK/OK/OK/OK/OK
上游 oiapi 外呼次数: 5（理想=1）
```

**代码依据**：`inflightCount`（L2466）只是并发**计数**，用于 `inflight >= maxConc` 时跳过本轮；没有"同歌同档共享同一个 Promise"的合并表。

**影响**：App 侧若同时发起播放 + 预加载 + 重试，同一首歌会重复打上游。上游配额是廉价资源，但 429 风险会叠加——而本项目刚为 429 设计了整条退避链路。

**分级的理由**：这不是"错误结果"，只是"多做功"。串行点歌场景（用户实际路径）每次 1 个请求，不受影响。

**未修**：请求合并属于新增机制（共享 Promise 后片段/失败结果如何分发、如何与缓存写点配合都需要设计），不是一行修补。

## G5 · 长时运行

**命令**：连续 200 次不同歌请求后读 `getHealthSnapshot()._memory`。

```
{"successCache":0,"failCache":200,"deliveryQuality":0,...,"limit":2000}
heapUsed: 6.7MB → 5.7MB
```

**事实**：200 条失败缓存未触及 300 上限；heap 未增长。

**局限（必须写明）**：这一轮的 200 次请求**全部失败**（探针场景被上一段污染成非法 URL），所以只验证了 `failCache` 的增长与上限，`successCache` / `deliveryQuality` / `fragmentSource` 三张表仍是 0，**没有验证到**。

**结论**：MEM 组已验证上限机制（`boundedMapSet`），但"真实成功路径下的长跑"仍未覆盖。记为 **G5 未完成**，不是通过。

## G6 · 安全面

**命令**：让上游依次返回四种非法 URL，观察是否交付。

```
javascript:alert(1)      → LINK_EXPIRED（不交付）
file:///etc/passwd       → LINK_EXPIRED（不交付）
data:audio/mp3;base64,xx → LINK_EXPIRED（不交付）
超长 https://a…(3000)    → LINK_EXPIRED（不交付）
200KB songmid            → LINK_EXPIRED，耗时 7ms
```

**事实**：四种都**不会被交付给 App**。防护是两道，不是一道：

1. `validateUrl`（L1497）用 `HTTP_URL_REGEX = /^https?:\/\//i` 做**显式协议白名单**。实测：`javascript:` / `file:` / `data:` / 协议相对 `//evil` 全部 `false`，`https://` / `HTTP://` / `HTTPS://` 全部 `true`。
2. 闸门开启时还有验真兜底。

实测代表码显示 `LINK_EXPIRED` 而不是 `PARAM_ERROR`，是因为非法 URL 先撞上了验真判据——**不代表没有白名单**。（初稿这里写"无协议白名单"，是未核实就下的推断，已纠正。）

**残留风险**：`verifyDelivery=false` 时仍由 `validateUrl` 单独守住，两道相互独立；但白名单只认 `http(s)`，对"合法 https 但指向内网/本地地址"没有拦截（本项目不含该场景，记为边界）。
