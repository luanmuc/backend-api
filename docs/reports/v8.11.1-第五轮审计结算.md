## 三、两个真实缺陷

### D-20：片段被当 FLAC 完整版交付

完整链路：`suyinKuwoGetUrl` 拿到 CDN 链接只做 `isAudioPlayable`（只验"能播"、不验时长）就 `setCachedUrl` 写三档缓存；内层三个 handler（`kuwoOfficial`/`suyinKuwo`/`suyinMigu`）都在验真之前写缓存；外层 `verifyDelivery` 确实识别了片段并标「试听版」，但缓存已经被内层写好；用户复播走缓存命中，那处验真对网络异常 fail-open，于是一个 5.3 秒片段被标成 FLAC、无任何标注交付——与手机截图（音质 FLAC、时长 00:03/00:05）完全对应。

修复：三处内层 `setCachedUrl` 全删，缓存统一由外层（验真后、带真实音质与子源）写。反向验证：把内层加回去 → W1 立刻红。

为什么四轮没抓到：前三轮按"缓存双入口"查（成功缓存 + 过期兜底），没查 **handler 自己写的第三入口**，而第三入口写的恰恰是唯一没验真过的 URL。也解释了 T5 为什么一直假绿：T5 判据是 `!subSourceName.includes('试听版')`，而缓存命中返回的 `subSourceName` 是空字符串，同样不含"试听版"。

### D-21：一个 NaN 让整个实例瘫痪

`manageConfig` 写入校验只有 `typeof value !== "number" || value <= 0`，NaN 从三道门全穿（`typeof NaN === "number"`、`NaN <= 0` 为 false、`NaN < min` / `NaN > max` 也是 false）。`raceBudgetMs=NaN` 写入后 `Date.now() + NaN = NaN`，每次请求竞速预算都是 NaN，**该实例所有请求立即 `NETWORK_TIMEOUT` 直到重启**。

证据不是推测：写 EDGE3/EDGE4 时两条断言同时变 `NETWORK_TIMEOUT`，查下来就是前一句 NaN 污染了整个实例。

修复：① 校验层加 `!Number.isFinite(value)`；② `cfg()` 对数值型默认值做有限数回落。
**诚实标注**：删掉 ② 后 EDGE5 仍绿，证明 ② 无可独立观测路径，属纵深防御，不算"已验证的修复"。

## 六、顺带验证出的设计事实

同一首歌连续失败**不会**累积到熔断阈值——整链全失败会写 30s 短失败缓存（`allFailShortTtlMs`），第二次直接返回缓存错误、不记账。源码注释写明这是刻意防雪崩（"避免同一首歌每次重播都在降级链里白跑 ≈18s"）。这意味着：**熔断累积要靠不同歌的真实失败**，测熔断必须用多首不同歌。

## 七、明确的未覆盖项

- 冷却到期 **±1ms**（`Date.now()` 不可控，只用"1.5s 后仍在冷却"下界近似）
- TTL 精确 **±1ms**（改用注入 TTL + sleep 近似）
- `songmid` 含 `|`（缓存键是拼接串，构造成本高、现实收益低）
- **429 连发**（走 `recordRateLimit` 独立分支，与 5xx 的 `recordFailure` 不同）
- **多源换源**（INV2 只在单源链路验证，`helloworldKw`/`kuwoOfficial` 的 mock 形状与 oiapi 不同，未构造）
