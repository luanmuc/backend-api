## 一、关联分析（先找共用构造，避免重复搭台）

剩余盲区看似零散，实际只有 **5 个构造源**。同一组内共用 helper，开发成本可摊薄一半：

| 组 | 覆盖对象 | 共用构造 | 预估条数 |
|---|---|---|---|
| **A 配置键** | `USER_CONFIG` 40 键「配了是否真生效」 | `fresh(cfg)` + 各键观察点 | 60~80 |
| **B 源错误分支** | 20 源的专属错误码与降级路径 | mock `fetchFault` 按 URL 分流 | 40~60 |
| **C 格式嗅探** | ogg/m4a/wav、FLAC 多 STREAMINFO、MP3 无 Xing、时长 `mm:ss` | `sniffAudioBytes` 头构造器 | 15~20 |
| **D 缓存/片段/并发** | 缓存命中校验失败、片段源过滤、并发合并、限流退避、播放摘除边界 | 脏缓存 + 片段判定 + `counts` | 30~40 |
| **E 变异看护** | D-32/D-33/D-34 三个修复的回归守护 | `run.js` 新变异体 | 8~10 |

**关联点（可合并的）**：
- A 的 `fragmentFallback` / `qualityShortCircuit` / `truthfulQuality` 与 D 的片段/短路构造**同源**，一次构造可两边用。
- B 的"源返回片段"与 D 的"片段源过滤"共用同一份片段响应体。
- C 的时长解析与 B 的"时长错配拒收"共用 `normalizeDurationSec`。

## 三、纪律（沿用前几轮）

1. **每批先红后绿**：新断言首次跑必须能因缺陷翻红，否则该断言是空转的。
2. **每批独立提交**，不推送（推送由用户决定）。
3. **反向验证**：对每个新"修"的缺陷，撤销修复必须让断言翻红。
4. **不锁缺陷现状**：发现缺陷要么修，要么写进 `AUDIT_RESULTS` 并显式标注"未修"，绝不写成断言说它是对的。
5. **g-meta 必须常绿**：M14 守"缓存写入唯一入口"，改读路径不受限、改写路径要重新论证。
