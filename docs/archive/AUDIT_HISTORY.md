#### 0. 为什么要从 v8.1 重做一版计划

v8.1 的 40 个维度 **全部判 ✅**，但 v8.1 之后连续 6 个版本（v8.2 → v8.10.2）仍在运行期出缺陷。复盘这 6 个缺陷的共同点：**v8.1 判的是"功能存在"，而缺陷出在"存在之后是否正确"**。

| v8.1 判据 | 实际出问题的形态 | v8.1 为何漏掉 |
|---|---|---|
| "try/catch 全覆盖，错误码结构化" | v8.10.2：先 `recordSuccess` 后 `validateUrl` → 同一请求双记账 | 存在性与结构正确 ≠ 记账序正确 |
| "LRU 上限 500 有界" | v8.10.1：LRU 缺 `delete` → 过期高音质缓存重播 TypeError | 只看容量边界，不看方法面完整性 |
| "冒烟 49 组覆盖核心路径" | T46–T48 曾是**空壳断言**（恒真） | 只数条数，不做反向验证 |
| "20 源端到端" | v8.2：`probeSingleSource` 漏透传 `method/body` → POST 源探活实发 GET | 抽查的是取链路径，探活另一条路径 |
| "假成功治理" | v8.7：huibq code=0 + 「无法获取播放链接」+ 可播错链 | 只审了"错误码是否分类"，没审"码为成功时内容是否属于目标" |
| "配置化治理" | v8.10.2 才补齐半开收口（业务失败/本地节流），**429 分支至今未收口** | 只审"参数是否可配"，不审"状态机每条出口是否都收口" |

**结论：v8.1 缺的是三类维度——运行正确性（状态机/记账/身份）、跨层契约（源 ↔ App fork）、证据有效性（用例是否真能抓错）。v9.0 保留 40 维，新增 56 维。**

#### 1. 三条方法论硬约束

1. **每条结论必须落到四元锚点**：`定义行号 → 调用方 → 被调用方 → 结果消费方`。只给文件名或"代码里有"不算证据。
2. **每个"正常"结论必须做反向验证**：构造能让它变红的输入。修复项回退后必须变红（红-绿）。空壳断言一律视为缺陷。
3. **证据分级**，禁止越级：
   - L0 静态阅读 / L1 `node --check` + mock 宿主加载 / L2 mock 宿主行为验证（含反向用例）/ L3 官方冒烟 `test/lx-source-smoke-test.js` / L4 真网络取链 + Range 可播 + 真机播放。
   - 环境不可达的维度标 `blocked`，**不得**用"代码里写了"冒充通过。本轮沙箱出口 IP 被三平台风控，L4 不可达。

#### 2. 判定与分级

| 级别 | 判据 |
|---|---|
| 高危 | 会让源/功能**永久或长期失效**，或让用户拿到错误结果且无法自愈 |
| 中危 | 指标失真、误判、可用性下降，有自愈路径或需 3 次以上才显现 |
| 低危 | 诊断信息失真、口径偏差、可维护性问题 |
| 建议 | 不改行为的设计优化 |

#### §0 为什么压「判据」而不只是压「流程」

前三轮压测（`stress-test` 12 条、`stress-round3` 14 条）主要压**流程**：能不能取到链、会不会崩、并发会不会炸。
但真正决定「用户听到什么」的是**判据**——什么算交付成功、什么算失败、什么算片段、什么该被拒。

判据错的时候，流程全绿也照样给错结果。所以 V 组只打判据。

#### §3 四条「压测自身翻过车」的组

### §3.1 V17：一次失败的自证

V17 最初用 `statusCode: 500` 造故障 → **短路从未达标**。真因：500 归 `recordBusinessFail`，
而短路只统计 `fail + linkExpired`。改用 `{error:'ECONNRESET'}` 才进统计。
端到端仍拿不到「放行后确有一次外呼」（被播放摘除 / 冷却 / 失败缓存三层叠加挡住），
故按授权加 `__debug` 只读钩子，落到**判据层**断言。

V17a 达标短路 / V17b 强制到期放行 / V17c 放行后立刻重新短路 / V17d `fail=2<3` 不短路。
双向反向验证：变异 A（到期 `return false`→`true`）→ V17b 红；变异 B（首次 `true`→`false`）→ V17a 红。

### §3.2 V19：绝对阈值不可靠

初版 `tSlow > 500` 在「把 `probeTimeout` 写死成 `HEALTH_CHECK_TIMEOUT`」的变异下仍绿（1000ms 也 >500）。
改为相对比较 `tSlow > tFast*3 && tSlow > 600` 后，该变异使两值趋同 → V19a/V19b 双双翻红。

### §3.3 V20：脏缓存不再把 128k 标成 FLAC

D-20 之前写槽用**请求档**，请求 flac 实给 128k 时会留下脏槽。命中路径已调 `verifyDelivery`
（`v.quality` 就是真音质）却只用来判 `ok===false`。修法：命中返回时用验真结果回填 `type`。

**M14 拦下过一次设计违反**：第一版在命中路径加 `setCachedUrl` 一起改槽位 → `g-meta`
报「缓存写入只有唯一入口，写点 2 处」。改为只回填标签、槽位留给下次正常写入修正。

### §3.4 V21：兜底档丢 singer 的实证（D-31）

`buildSearchKeywords` 三级，末级 `strict:false` 只传 `{name, duration}`，
`songInfoMatch` 的歌手校验（`if (songInfo?.singer && singer && ...)`）**整条被跳过**。

| 断言 | 场景 | 结果 |
|---|---|---|
| V21a | 严格档（带歌手）遇错歌手 | 抛 `SONG_MISMATCH`，拒绝 |
| V21b | 兜底档遇**同一条**错歌手 | 放行并交付（会播错歌） |
| V21c | 兜底档放行必须落日志 | 实测 stdout 捕获到 1 条 |

V21c 观测踩了三轮：patch `console.log` 抓不到（`safeConsole.log` 是**加载期** `console.log.bind(console)`）
