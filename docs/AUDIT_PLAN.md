## 0. 为什么要从 v8.1 重做一版计划

v8.1 的 40 个维度 **全部判 ✅**，但 v8.1 之后连续 6 个版本（v8.2 → v8.10.2）仍在运行期出缺陷。复盘这 6 个缺陷的共同点：**v8.1 判的是"功能存在"，而缺陷出在"存在之后是否正确"**。

| v8.1 判据 | 实际出问题的形态 | v8.1 为何漏掉 |
|---|---|---|
| "try/catch 全覆盖，错误码结构化" | v8.10.2：先 `recordSuccess` 后 `validateUrl` → 同一请求双记账 | 存在性与结构正确 ≠ 记账序正确 |
| "LRU 上限 500 有界" | v8.10.1：LRU 缺 `delete` → 过期高音质缓存重播 TypeError | 只看容量边界，不看方法面完整性 |
| "冒烟 49 组覆盖核心路径" | T46–T48 曾是**空壳断言**（恒真） | 只数条数，不做反向验证 |
| "20 源端到端" | v8.2：`probeSingleSource` 漏透传 `method/body` → POST 源探活实发 GET | 抽查的是取链路径，探活另一条路径 |
| "假成功治理" | v8.7：huibq code=0 + 「无法获取播放链接」+ 可播错链 | 只审了"错误码是否分类"，没审"码为成功时内容是否属于目标" |
| "配置化治理" | v8.10.2 才补齐半开收口（业务失败/本地节流），**429 分支至今未收口** | 只审"参数是否可配"，不审"状态机每条出口是否都收口" |

**结论：v8.1 缺的是三类维度——运行正确性（状态机/记账/身份）、跨层契约（源 ↔ App fork）、证据有效性（用例是否真能抓错）。v9.0 保留 40 维，新增 56 维。**

## 1. 三条方法论硬约束

1. **每条结论必须落到四元锚点**：`定义行号 → 调用方 → 被调用方 → 结果消费方`。只给文件名或"代码里有"不算证据。
2. **每个"正常"结论必须做反向验证**：构造能让它变红的输入。修复项回退后必须变红（红-绿）。空壳断言一律视为缺陷。
3. **证据分级**，禁止越级：
   - L0 静态阅读 / L1 `node --check` + mock 宿主加载 / L2 mock 宿主行为验证（含反向用例）/ L3 官方冒烟 `test/lx-source-smoke-test.js` / L4 真网络取链 + Range 可播 + 真机播放。
   - 环境不可达的维度标 `blocked`，**不得**用"代码里写了"冒充通过。本轮沙箱出口 IP 被三平台风控，L4 不可达。

## 2. 判定与分级

| 级别 | 判据 |
|---|---|
| 高危 | 会让源/功能**永久或长期失效**，或让用户拿到错误结果且无法自愈 |
| 中危 | 指标失真、误判、可用性下降，有自愈路径或需 3 次以上才显现 |
| 低危 | 诊断信息失真、口径偏差、可维护性问题 |
| 建议 | 不改行为的设计优化 |

### S 组 · 语义契约与 action 返回结构（2026-08 之后新增，2026-11-08 补判据）

> 来源：第二轮全覆盖审查。音源侧没有 UI 文案，本组聚焦两件事：
> ① App 对返回值的**语义假设**是否与音源实际返回一致；② 错误是否被静默吞成"空结果"。

### 触发案例（2026-11-08）

听歌统计：侧边栏文案是「今日 {today} 次 · 时长 {time}」，实际传的是累计 `playTime`。
类型全对（都是 number）、40 条文档规则全绿、`check_ts_syntax` 0 错误——**功能是错的**。

### 根因：判据太宽，执行时被简化

原计划里的 i18n / 状态机 / 持久化 组，执行时被落成"键数对不对""字段有没有"，没有落到
"文案说的意思 **vs** 数据实际的意思"。这类缺陷在单文件纵向读时处处自洽，只有横向穿才看得见。

### 三条硬判据（改动 UI 展示 / 统计 / 配置时必须过）

1. **文案 ↔ 字段横向穿**：每个带参 `t()` 填五行表
   `文案键 → 占位符 → 传入表达式 → 字段定义 → 写入点`，任一处语义不符即缺陷。
   易错语义词：今日/累计/剩余/总数/上次/平均/速度/已下载/本次/总时长。
2. **类型正确不算通过**：`playTime` 与 `dayTime` 都是 number，编译器不会警告；
   必须人工确认"这个数字语义上是不是文案要的那一个"。
3. **"改过"不等于"审过"**：注释里的"已修正"只证明被碰过一次，不证明展示层被审查过。

### 三类假阳性（写报告前必须过滤，否则制造假缺陷）

| 假阳性 | 成因 | 过滤方法 |
|---|---|---|
| 文案占位符"缺参" | 脚本不认 ES6 属性简写 `{ name }` | 回读源码确认调用形态 |
| "设置项没人读" | 正则漏 `useSettingValue('...')` / 动态 key | 用短名全仓 grep 复核 |
| "导出零引用=没接线" | 可能是有意保留的上游死代码 | `git log -S '<符号>'` 回查引入提交再定性 |

### 一条跨仓新判据

**依赖版本"落后"不等于"有问题"**：App 锁定 fork sha 落后 9 个提交，需先看这 9 个提交的性质
（本例全为 docs/hooks，零代码变更 → 无风险），不能只比较 sha 差异就判缺陷。
